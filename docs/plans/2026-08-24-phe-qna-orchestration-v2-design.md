# PHE Q&A Orchestration V2 Design

Date: 2026-08-24
Status: Approved by the supplied production brief
Baseline: `46b6dea0e1c883d4a703a9b75877151aba344908`

## Audit conclusion

The current Q&A path rejects questions through `HEALTH_SCOPE_MARKERS` before DeepSeek can
understand them, assembles the full evidence bundle for every accepted question, and invokes
MedGemma before the DeepSeek candidate exists. Conversation rollover and the separation between
conversation semantics and health-fact authority are already correct and remain unchanged.

## Approaches considered

1. Rewrite only `services/qna.py`. This minimizes file count but mixes model schemas, evidence
   selection, deterministic data queries, medical gating, finalization, persistence, and chat
   lifecycle in one large service.
2. Add a focused L7 Q&A orchestration module and extend the existing L7 product adapter. This
   reuses the sealed DeepSeek/MedGemma transports while keeping deterministic policies testable.
3. Introduce a generic workflow engine. This would be flexible but is unnecessary for one product
   flow and would expand the sealed L7 surface substantially.

Approach 2 is selected. It is the smallest design that keeps routing, evidence selection, medical
gating, hallucination validation, finalization, and audit independently verifiable.

## Architecture

Every non-empty question is stored in the existing conversation, then sent with only a bounded
recent semantic history to `ProductDeepSeekReasoningAdapter.classify_question`. The production
adapter uses the existing `RealDeepSeekReasoningModelAdapter._chat`, which already enforces
`deepseek-v4-flash`, temperature 0, JSON output, and disabled thinking. Keywords may remain only
inside deterministic safety gates or test mocks; they have no production scope authority.

The classifier returns a strictly validated routing object with scope, intent, decision type,
canonical domains and metrics, evidence need, time range, aggregation, medical consequence,
medical-review hint, and potential-context semantics. Invalid or unavailable classification fails
explicitly instead of guessing or falling back to keyword scope.

Routing is deterministic after classification:

- `PRODUCT_META`: fixed Chinese product identity, no evidence, reasoning, or medical model.
- `OUT_OF_SCOPE`: fixed refusal, no evidence, reasoning, or medical model.
- `HEALTH_DATA`: deterministic L3 query over a canonical metric registry. Values, windows,
  aggregation, units, and provenance come from the engine; MedGemma is normally bypassed.
- `HEALTH_CONTEXT`: formal context extraction/write semantics when the classifier identifies a
  clear user-reported fact; otherwise it remains conversation semantics only.
- `HEALTH_DECISION`: assemble the sealed evidence bundle, deterministically select only relevant
  domains/metrics/context/patterns, generate candidates, and call DeepSeek Stage B.

Stage B returns a strict candidate with direct answer, reason, actions, confidence, evidence refs,
medical claims, and uncertainties. Evidence refs must be a subset of the catalog generated by the
question bundle. Deterministic validation rejects missing refs, unsupported facts, diagnosis-like
claims, and malformed Chinese output before it can reach the user.

The final Medical Consequence Gate combines classifier consequence, decision type, sealed L6
medical triggers, current Today medical state, and candidate claims/actions. Physical-activity
decisions, high-consequence advice, symptom/disease/drug/doctor questions, sealed safety triggers,
and suspicious candidate claims require review. Deterministic low-consequence data lookups bypass
review.

When review is required, MedGemma receives the user question, question-specific evidence bundle,
and complete DeepSeek candidate. The deterministic finalizer handles every review state:

- `APPROVED`: use the validated candidate.
- `APPROVED_WITH_CHANGES`: ask DeepSeek for one constrained structured correction using only the
  candidate, evidence, and required changes; revalidate against the same evidence catalog.
- `REJECTED`: suppress the candidate and return a fixed evidence-insufficiency answer.
- `ESCALATE`: use restrained fixed safety language plus the reviewer escalation reason.
- `UNAVAILABLE`: fail closed for required review and never expose the unreviewed candidate.

No chain-of-thought, prompts, raw model payloads, secrets, or internal evidence IDs enter the API or
chat transcript. Structured classification, candidate, medical result, finalization path, model
identities, and call decisions are persisted in a new L7 `qna_audits` table. Existing L6
`qa_sessions` and `medical_reviews` remain the health-reasoning audit authority.

## Flutter UX

The synchronous API contract remains compatible. While a request is pending, the Q&A screen moves
through bounded user-facing status copy: understanding, combining personal data, and (for a long
request) safety checking if needed. The existing inference timeout, sanitized failure, and retry
path remain authoritative. Model names and internal states are never shown.

## Verification

Tests are written first for semantic scope, follow-up context, deterministic health-data values,
question-specific evidence, candidate-before-review ordering, all finalizer states, hallucination
rejection, fail-closed review, sanitized audit persistence, context authority, and Flutter loading
states. Full backend, L6 adapter, Flutter analyzer/tests, upstream integrity, static model audit,
secret audit, VPS deployment, authenticated real-model Q&A cases, public-port checks, daily service,
and timer state are required before sealing.
